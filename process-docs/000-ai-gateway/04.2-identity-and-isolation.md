> **This slice amends a locked decision.** AD-7 of the approved build plan says
> identity reaches the connection by `SET LOCAL` inside the work transaction.
> That is necessary and **not sufficient**, and shipping it alone would have
> leaked every row. Section 6 has the evidence and the corrected design. A change
> record is filed against [the build plan](./03-build-plan.md).

## 1. What works when this lands

A request carrying a Supabase JWT resolves to a `user_id`, and every database
statement it makes runs inside a transaction that carries that identity and
cannot see another user's rows. A test proves the isolation holds by failing
closed: with no identity set, the query returns nothing rather than everything.

## 5. Internal contracts

### Settings additions

```python
database_url: str                      # no default. Missing stops the process
supabase_url: str
supabase_jwks_url: str
db_pool_size: int = 5
jwks_cache_seconds: int = 600          # Supabase caches JWKS for 10 minutes
```

`secret_values()` returns the database password, parsed out of `database_url`,
so it is redacted from logs. A connection error from asyncpg renders the DSN,
and the DSN carries the password.

### The identity-bearing transaction

```python
@asynccontextmanager
async def user_transaction(
    session: AsyncSession, user_id: UUID | None
) -> AsyncIterator[AsyncSession]:
    """Open a transaction that RLS will actually police."""
```

Section 6 is why this exists and why both statements are mandatory.

### Auth

```python
async def verify_token(token: str, settings: Settings) -> UUID:
    """Return the user id from a valid Supabase JWT.

    Raises InvalidToken on a bad signature, a wrong issuer, or expiry.
    """
```

`sub` is the user id. `iss` must equal `{supabase_url}/auth/v1`. Keys come from
the JWKS endpoint and are cached for `jwks_cache_seconds`, which is capped at
Supabase's own 10 minutes so a rotated key is picked up rather than rejected.

## 6. The isolation mechanism, and why AD-7 is amended

### What was measured

Run against the live database on 2026-09-12, on a probe table with RLS enabled,
forced, and a correct policy on `user_id`.

| Configuration | Rows user 1 could see, of 2 | |
|---|---|---|
| `FORCE ROW LEVEL SECURITY` plus `SET LOCAL request.jwt.claims` | **2** | every row leaked |
| The same, plus `SET LOCAL ROLE authenticated` | 1 | correct |
| The same, with no claim set | 0 | fails closed |

### Why the first row leaks

`postgres` on Supabase is not a superuser, but it carries `rolbypassrls`.

| Role | `rolbypassrls` |
|---|---|
| `postgres`, which the application connects as | **true** |
| `service_role` | true |
| `authenticated` | false |
| `anon` | false |

`BYPASSRLS` outranks `FORCE ROW LEVEL SECURITY`. Forcing the table closes the
*owner* exemption; it does nothing about the *bypass* privilege. The policy is
never evaluated, so the table looks correctly configured and every query returns
everything.

**This is the failure T-Q2 of the tech stack describes: isolation disabled with
no error.** It was found by measuring rather than by reading, and a positive test
alone would not have caught it: user 1 querying their own row returns that row
under both configurations.

### The corrected design

Every request-scoped transaction runs both statements, in this order:

```sql
SELECT set_config('request.jwt.claims', '{"sub":"<user_id>"}', true);
SET LOCAL ROLE authenticated;
```

1. **Claims first**, because the role switch drops privileges and the claim is
   what the policy reads.
2. **`SET LOCAL ROLE authenticated`**, which drops `rolbypassrls` for the
   transaction. Verified to reset to `postgres` on commit, so a pooled
   connection cannot carry the role forward.
3. Both are `LOCAL`. Neither survives the transaction.

Every table therefore needs `GRANT SELECT, INSERT, UPDATE, DELETE ... TO
authenticated`, because after the switch the connection holds only what that
role is granted. A migration that creates a table without the grant produces a
permission error rather than a leak, which is the right way round.

### What the application never does

Rule T3. The application holds no service-role credential and never sets
`row_security = off`. Migrations run as `postgres` over the same
`DATABASE_URL`, which is correct: DDL is unaffected by RLS, and a migration that
had to bypass a policy would be a design error.

**Operator reads for FR-14 are out of scope here.** The operator queries through
Supabase's dashboard, which connects with a privileged role. No application code
path reads another user's rows, and none is built.

## 7. Error handling

| Failure | Detected by | User sees | System does |
|---|---|---|---|
| No `Authorization` header | `IsAuthenticated` | GraphQL error, `UNAUTHENTICATED` | Nothing reaches a resolver |
| Malformed or expired token | `verify_token` | GraphQL error, `UNAUTHENTICATED` | Logs the failure reason, never the token |
| Signature does not verify | `verify_token` | The same generic error | Logs at warning. Deliberately indistinguishable from expiry, so the message cannot be used to probe |
| Issuer mismatch | `verify_token` | The same generic error | Logs at warning with the received issuer |
| JWKS endpoint unreachable | `httpx`, inside PyJWT | GraphQL error, `SERVICE_UNAVAILABLE` | Serves from the cache if unexpired, otherwise fails. Never skips verification |
| Database unreachable | Engine | GraphQL error, `SERVICE_UNAVAILABLE` | `/health` continues to report liveness. Readiness reports the failure |
| A statement runs outside `user_transaction` | Review, and T-2.7 | Nothing | Cannot be caught at runtime. T-2.7 is the guard |

**A token failure never says which check failed.** Distinguishing expiry from a
bad signature tells an attacker which half of a forged token to fix.

## 8. Test plan

| id | Level | Case | Covers |
|---|---|---|---|
| T-2.1 | unit | A token signed by the wrong key is rejected | FR-7 |
| T-2.2 | unit | An expired token is rejected | FR-7 |
| T-2.3 | unit | A token whose `iss` is not `{supabase_url}/auth/v1` is rejected | FR-7 |
| T-2.4 | unit | A valid token returns the `sub` claim as a `UUID` | FR-6 |
| T-2.5 | integration | A GraphQL field with `IsAuthenticated` and no header returns an error and touches no database session | FR-7 |
| T-2.6 | integration | User A inserts a row, user B queries the table, and sees **zero** rows | FR-6, T7 |
| T-2.7 | integration | With **no** claim set, a select returns **zero** rows, not all rows | T2, section 6 |
| T-2.8 | integration | After a transaction commits, `current_user` is `postgres` and `request.jwt.claims` is empty | section 6 |
| T-2.9 | integration | Every table in `public` has `relrowsecurity` and `relforcerowsecurity` true | T2 |
| T-2.10 | integration | A connection error's log line does not contain the database password | FR-3 |

**T-2.7 is the test that matters most.** It is negative, and it is the only one
that distinguishes "the policy ran and excluded rows" from "the policy never
ran". T-2.6 passes under the leaking configuration; T-2.7 does not.

T-2.9 is the standing guard: it fails the day someone adds a table without a
policy, which is exactly how rule T2 erodes.
