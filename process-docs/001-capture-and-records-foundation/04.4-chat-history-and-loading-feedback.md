## 1. What works when this lands

The Capture page has a history action that opens a panel of every past capture
turn, most recent first, surviving a reload. Submitting a command, answering a
pending question, and saving the task edit form each show a loading state
instead of nothing between click and response.

## 2. Requirements covered

| FR | How this slice satisfies it |
|---|---|
| FR-44 | Every call to `submitCapture` (the add-task path only, not `/tasks`), `answerPendingCapture` and `discardPendingCapture` writes one `capture_turns` row after its outcome is known. `resulting_task_id` and `resulting_pending_capture_id` are set whenever that outcome applies, so an answered question's row correlates back to the row that first asked it. `question_text` and `answer_text` are captured onto the turn itself, not read from `pending_captures` at display time, because that row is deleted once resolved (FR-37) — without this, history would lose the question and answer wording for exactly the entries it most needs to show |
| FR-45 | A history icon in the Capture topbar opens `HistoryPanel`, which queries `captureHistory`, paginated, newest first |
| FR-46 | `CommandCenterController` tracks which turn's answer is in flight and disables that turn's answer control with an inline spinner; `RecordEditForm` gets an `isSaving` prop driven directly by `useUpdateTask()`'s existing `apiStatus`, no new state needed there |

## 4. A gap found while drafting this, not fixed here

`RecordEditForm` renders due date read-only; there is no control to change it.
`completeTask` exists as a mutation with no UI calling it — completion happens
by setting status to Done in the same edit form, through `updateTask`. FR-19's
"any field the user supplied" is not fully built for due date. This slice adds
loading feedback to the Save action that exists; it does not add the missing
due-date control or wire up `completeTask`. Named here so it is not silently
assumed done, same treatment as 04.3 §6's reload gap.

## 6. Interfaces and contracts

```python
# app/domains/capture/interfaces/dtos.py
CaptureTurnOutcome = Literal["task_created", "question_asked", "discarded", "refused"]

@dataclass(frozen=True)
class CaptureTurnDTO:
    id: UUID
    input_text: str
    outcome: CaptureTurnOutcome
    resulting_task_id: UUID | None
    resulting_pending_capture_id: UUID | None
    question_text: str | None
    answer_text: str | None
    created_at: datetime

@dataclass(frozen=True)
class CaptureHistoryPageDTO:
    items: list[CaptureTurnDTO]
    next_cursor: str | None
```

```python
# app/domains/capture/interfaces/repositories.py
class CaptureTurnRepository(Protocol):
    async def record_turn(
        self, *, user_id: UUID, input_text: str, outcome: CaptureTurnOutcome,
        resulting_task_id: UUID | None, resulting_pending_capture_id: UUID | None,
        question_text: str | None, answer_text: str | None,
    ) -> None: ...

    async def list_turns_for_user(
        self, *, user_id: UUID, cursor: str | None, limit: int,
    ) -> CaptureHistoryPageDTO: ...
```

```graphql
enum CaptureTurnOutcome { TASK_CREATED QUESTION_ASKED DISCARDED REFUSED }

type CaptureTurn {
  id: ID!
  inputText: String!
  outcome: CaptureTurnOutcome!
  resultingTaskId: ID
  resultingPendingCaptureId: ID
  questionText: String
  answerText: String
  createdAt: DateTime!
}

type CaptureHistoryPage {
  items: [CaptureTurn!]!
  nextCursor: String
}
```

`captureHistory(cursor: String, limit: Int): CaptureHistoryPage!` on `Query`,
`IsAuthenticated`. Cursor is opaque to the client: base64 of
`"<created_at ISO>|<id>"`, decoded only by the repository.

## 8. State management

| State | Lives in | Lifetime | Invalidated by |
|---|---|---|---|
| History panel open/closed | `CommandCenterController` component state | One composition | Toggle click |
| History pages | `useGetCaptureHistory`'s query result, read directly by `HistoryPanel` | Session, refetched on panel open | Not cached across opens: `network-only`, per the frontend's transport-only Apollo rule. No MobX store: history is read-only and never written back to by another mutation in the same tab, unlike `records`/`tasks` |
| `submittingTurnId` | `CommandCenterController` component state | One in-flight answer | Set on submit, stale once `answerApiStatus` leaves `API_FETCHING` — read together, never cleared by itself |

## 9. Error handling

| Failure | Detected by | User sees | System does |
|---|---|---|---|
| `captureHistory` fails (network, auth) | `useGetCaptureHistory`'s `apiStatus` | Error state in `HistoryPanel`, per design §4, with retry | No turn data lost: this is a read, nothing was written |
| A capture turn fails to write after a successful `submitCapture`/`answerPendingCapture` (repository error) | Caught at the interactor boundary | Nothing — the user's task or question already succeeded and is shown normally | Logged as a warning, not raised past the interactor: FR-44 says a turn is retained, not that a write failure may undo an otherwise-successful capture. `NFR-9`'s "no capture is lost" binds the task/question, not the log of it |
| Two answers submitted from two different pending turns in quick succession | `submittingTurnId` tracks only the most recent | The first turn's spinner clears early, incorrectly, if a second answer starts before the first resolves | Accepted as a known edge case, not fixed here: answering two different pending questions inside the same second is not a flow FR-37 or FR-46 describe, and `useAnswerPendingCapture`'s single mutation tuple would need per-call tracking to fix properly, which is more than this slice's scope |
