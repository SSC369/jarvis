## 1. What works when this lands

A user opens Records, sees every task in one table, filters to Tasks, searches
by title, opens one, edits its title or marks it done, deletes it with
confirmation. In Settings, they see their detected timezone and change it.

## 6. Error handling

| Failure | Detected by | User sees | System does |
|---|---|---|---|
| `updateTask`/`completeTask`/`deleteTask` on an id that does not exist or belongs to another user | `TaskRepository.get_by_id` returns `None` (RLS already hid the row) | `RecordNotFound` mapped to a toast; the row disappears from the list on next fetch | No write |
| `updateTask` called with neither `title` nor `status` | `UpdateTaskInteractor._validate_has_a_field` | Frontend prevents this by disabling Save until a field changes; the server check exists because the client is not trusted alone | No write |
| `deleteTask` with more than one id | N/A, this is the expected multi-delete path | `DeleteConfirmModal` states the count before the mutation fires, per FR-21 | One `DELETE ... WHERE id = ANY(...)`, RLS-scoped |
| `updateTimezone` with a string `zoneinfo` cannot parse | `UpdateTimezoneInteractor._validate_timezone` | `InvalidTimezone`, current value kept, per design §4 Settings "Error" state | No write |
| Browser cannot detect a timezone (`Intl` throws or returns `undefined`) | `detectTimezone.ts` | Falls back to `identity.constants.DEFAULT_TIMEZONE` ("UTC"), shown as a normal value the user can change | `GetSettingsInteractor` still creates a row on first read, with `"UTC"` |
