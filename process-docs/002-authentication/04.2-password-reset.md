## 1. What works when this lands

A person who forgot their password requests a reset from Sign in, proves the
email is theirs with a mailed code, sets a new password, and signs in with it.

## 2. Requirements covered

| FR / NFR | How this slice satisfies it |
|---|---|
| FR-12 | `ForgotPasswordController`, `supabase.auth.resetPasswordForEmail` |
| FR-13 | `ResetPasswordController`, code step: `supabase.auth.verifyOtp` with `type: "recovery"`. Password step: `supabase.auth.updateUser` |
| FR-14 | Supabase's own code expiry, unchanged from FR-6's mechanism |
| NFR-4 | Supabase's native per-user OTP-send limit (confirmed while drafting `03-build-plan.md`: 60s window) already covers reset-code resend; no code here enforces it separately |

## 5. Internal contracts

None cross this slice's own boundary; `verifyOtp`'s `type: "recovery"` argument
and `updateUser`'s shape are Supabase SDK types, not ours.

## 6. Error handling

| Failure | Detected by | User sees | System does |
|---|---|---|---|
| Malformed email | Client-side check before submit | `02-design.md` Forgot password, error state | No request sent |
| Reset requested past Supabase's native OTP rate limit | `resetPasswordForEmail` error code | Forgot password, the "Too many requests" state | Nothing written; matches FR-18's already-accepted posture, no new lockout table |
| Wrong or expired code | `verifyOtp` error code | Reset password, code step's error state | Nothing written |
| Network failure, any call | Thrown/rejected promise | Generic retry-safe error | No optimistic state changes |
