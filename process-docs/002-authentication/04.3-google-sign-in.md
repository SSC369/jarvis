## 1. What works when this lands

A person signs up or signs in with "Continue with Google" on Sign up or Sign
in, skipping password and code entirely. An email that already has a manual
account signs into it, not a second one.

## 5. Internal contracts

```sql
-- handle_new_user(), replacing slice 1's version (migration 0007)
-- unchanged: still fires on auth.users insert, still writes profiles
-- new: if NEW.raw_user_meta_data->>'username' is null,
--       username := 'user_' || substr(NEW.id::text, 1, 8)
-- collision is not possible: auth.users.id is a UUID, the substring
-- is not separately unique-checked, but a UUID prefix collision is not a
-- realistic risk at V1's scale. Revisit only if it ever fires.
```

The `index.md` §4 open item this closes: a Google-created `profiles` row is
never left with a null username, generated instead. `profiles.username`
stays nullable at the schema level; nothing currently writes a null through
this path.

## 6. Error handling

| Failure | Detected by | User sees | System does |
|---|---|---|---|
| Google OAuth denied or cancelled by the user | `signInWithOAuth` redirect returns an error param | Back on Sign up/Sign in, unchanged, no error banner (the person chose to cancel) | Nothing written |
| Google account's email belongs to an unverified manual account | Supabase Auth's own linking rule (build plan §9: unverified emails are never auto-linked, to prevent pre-account takeover) | Supabase's own error, surfaced as the generic sign-in error state | No merge, no new account either; this is Supabase's behavior, not ours to change |
| Network/provider failure | Thrown/rejected promise, or Google's own error page | Generic retry-safe error | Nothing written |
